# T4.2 — Deploy production, drill rollback, close the record

## Why this task exists

The launch is not the deploy; it is the checks after it and the ability to go back. This task produces both
and makes the repository's status truthful.

## Pre-conditions

- T4.1 passed on the preview.
- Production domain and account id are configured; no placeholder remains.

## What to do

1. Deploy production through the workflow, not by hand:

   ```bash
   gh workflow run deploy-edge.yml --ref main   # or merge the approved change
   ```

   `VERIFY:` the workflow supports `workflow_dispatch`; if not, trigger by merge and record that.

2. Repeat T4.1's checks against `https://<domain>`; record statuses, canonical origin, and headers.

3. Drill rollback: deploy the previous commit's build, verify the two key routes, then redeploy the current
   build. Record both durations against the 10-minute budget.

4. Watch for 30 minutes: Worker 5xx in `wrangler tail`, and one manual page load at the end.

5. Update `docs/status.md` from observations: remove P0 rows that are verified fixed, add anything the watch
   revealed, update the snapshot line.

## Touches

- Production Worker `blog-edge-production`
- `docs/status.md`

## Verification

- Production checks match the preview for pages, feeds, sitemap, search, headers, and 404.
- Rollback measured in both directions, under 10 minutes.
- Status diff reviewed against the evidence list.

## Code style

## Risks

- DNS propagation can make a correct deploy look wrong; verify the served body, not the cached page.
- A rollback that only swaps the Worker version without re-uploading assets can mix versions; redeploy the
  whole build.
- Rollback of this task is a docs revert; it has no runtime effect.
