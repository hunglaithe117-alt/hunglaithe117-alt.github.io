# T3.1 — task memory

Completed 2026-11-19.

## What changed

`.github/workflows/deploy-edge.yml`:

- Both jobs replaced the aggregate `pnpm turbo run build --filter=./apps/edge...` with the same pair:
  `pnpm turbo run build --filter=@blog/web` (env `PUBLIC_SITE_URL: ${{ vars.PUBLIC_SITE_URL }}`) and
  `cd apps/edge && pnpm exec cf build --mode production` (env `SITE_DOMAIN` in the validate job,
  `CLOUDFLARE_ACCOUNT_ID` + `SITE_DOMAIN` in the deploy job).
- Deploy stays `cf deploy --prebuilt --mode production`; the mode now matches the artefact.
- Added `workflow_dispatch` and widened the `deploy` job condition to
  `!cancelled() && (dispatch || push-with-edge-change)`, so a manual re-deploy and the rollback drill
  reuse the gated job.
- No migration, secrets file, or container rollout step remains (removed in Phase 2).

`apps/edge/package.json`: the `build` script carries `--mode production`, so the Turbo graph and the
workflow produce the same artefact (previously a mode-less `cf build`).

`turbo.json`: `build.env` simplified to `["PUBLIC_*"]`; `@blog/edge#build.env` adds `SITE_DOMAIN`, which
strict `envMode` would otherwise hide from the build.

```text
  -> no matches
```

The filter regex `^(apps/(edge|web)/|packages/|pnpm-lock\.yaml|turbo\.json)` is unchanged and matches
`apps/web/...` and `apps/edge/...` paths.

## Deviations

- The plan's step 1 used `pnpm turbo run build --filter=@blog/web` for the web build and an explicit
  `cf build --mode production`; that is exactly what landed. The extra `apps/edge` script change was
  required so `pnpm build` (CI affected build, local build) cannot produce a mode-less artefact.
